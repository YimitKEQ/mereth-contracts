Each contract is a leaf of the register. The wax seal carries its state, so an unpaid promise reads as a seal broken across the middle at a glance. The fee, the funding flag and what you may do about it sit in the ruled margin, where a clerk would have put them.

Two ideas carry the weight

The first

Funded or unfunded, and everyone can see which

A funded contract takes the coin the moment it is posted and holds it. Whoever takes the work is certain of payment. An unfunded one binds nothing, so taking it is a bet on the client's word.

That single visible flag turns reputation from a number into a question players actually ask each other: will anyone work for you on your word alone?

The second

A promise that breaks becomes an object

When an unfunded contract is delivered and the client cannot pay, nothing errors. A debt note is written and sealed, naming both parties and the contract it came from. Anyone can read it. A broken promise stops being a failure state and starts being evidence.

The default path

server/contracts/contract.ts

The engine is pure. It never touches the game, so it tests headless, and it decides nothing about who was right.

Coin is never invented

server/contracts/escrow.ts

Two rules govern everything that moves money. Never create coin: every septim paid out was first taken from somebody. And take before you promise, so a failure leaves no contract rather than an unpayable one.

A player cannot act as somebody else

server/contracts/wire.ts

The client names an action and a contract id. It never names the actor. That comes from the connection, which is the whole authorization story in one line.

What a player is called

server/contracts/identity.ts

Worth calling out, because the obvious call is the wrong one and it took a live server to notice. Every player character is built on the same base record, the vanilla player NPC_ at 0x7, which is named Prisoner. So getActorName reported that Prisoner had posted work for Prisoner and Prisoner had taken it.

The name a player chose lives in the character's appearance, and it is the same string SkyMP puts above their head: the client runs refr.setDisplayName(model.appearance.name, true) on every appearance update. The stable identity is profileId, not the form id, which is reassigned on every connect.

What it took to find

undocumented

Four things gate the server-to-client channel. Each fails silently: no error on either side, the client simply never learns the properties exist. None are in the published docs, and the first exists only as a string inside scam_native.node.

GateWhat you see when it is wrong
enableGamemodeDataUpdatesBroadcast Server logs skipping gamemode data update send and never ships the channel.
server-info-ignore createClientSafe :0. The client resolves no peer and never connects at all.
serverKey + server-public-keys Pushed JavaScript is rejected with no signature found and deleted.
Debug.messageBox A modal box pauses the game loop, and updateOwner only runs on update. Every push freezes while it is on screen.

How work actually gets finished

not honour

A funded contract holds real coin between the moment work is claimed done and the moment it is paid for. Whoever gets to end that standoff on their own can rob the other one, so it depends on what was promised.

What was promisedHow it ends
Goods, funded Machine checked. The server counts the items out of the worker and into the client before it will record a delivery, then pays immediately. Nobody is taken at their word.
Service, funded The worker reports it done and the escrow stays held. The client has two days to accept or refuse. Say nothing and it releases to the worker.
Service, unfunded The client settles it themselves. If they cannot pay, a sealed debt note is written naming both parties.

The middle row is the one that matters, and it started out wrong. A funded service used to pay the instant the worker pressed the button, which meant anyone could take a funded job, claim it finished and walk off with the escrow. Expiry made the mirror image possible: a client who ignored finished work until the deadline got their coin back.

Now expiry refuses to touch delivered work, and the review window closes the other side. A refusal is still recorded against both parties and judged by neither, which is the part that stays social.

Does it run on your client

checked against your published bundle

Not a guess. Your client is public in BStarRP_SkyMP_Data, so every mechanism this depends on was checked against the 7.5 MB bundle your launcher ships, not against upstream skymp.

What this needsIn your client
updateOwnerFunctionsPresent. Gamemode property handlers compile the same way.
updateGamemodeDataMessagePresent. The channel that carries them is intact.
ServerJsVerificationServicePresent, with the skymp:sig:y: prefix. Signing works unchanged.
eventSourceContexts, sendEventPresent. Player actions reach the server by the same route.
browserMessagePresent, and used heavily. 58 call sites.
SweetTaffyEvalServiceRemoved. Only my unattended test harness used it. The feature does not.

The one thing that would have broken: your client drives its own React interface with browser.loadUrl and browser.setVisible, so anything of mine that claimed the browser would wipe your UI off the screen. It does not. The push calls a global if one exists and dispatches a CustomEvent, which is the same way your client already hands data to your own interface. Both are no-ops when nothing is listening.

So a component of yours listening for mereth:contracts gets the board, and the standalone panel above is there for the case where you would rather not build one.

Running it on your own server

four steps, no coordination with me

Nothing here needs my involvement. Take the folder, wire four lines into your gamemode, set two settings, and the server tells you on boot whether it works.

How you check I am not lying

before you trust a line of it

The contract engine tests itself against your live server on every boot, using your ESPM data and your database. No harness, no fixtures, nothing to install. Start the server and read the log.

That run posts real contracts, binds real coin, defaults one on purpose and writes the debt note, then checks the arithmetic. If it prints anything but CONTRACTS OK, do not ship it, and the failing line names what broke.

  • Then try to break it in game. Post a funded service, mark it delivered from the worker's side, and watch the escrow refuse to move until the client answers.
  • Try to steal from yourself. Take your own contract, settle work you did not do, refuse a delivery you were not party to. Every one is refused by the server and told to you in words.
  • Pull the plug. Contracts live in server properties, so restart mid-contract and the board comes back exactly as it was.
  • Read it. 1,293 lines of TypeScript across six files, nothing imported outside node:crypto and the SkyMP types. The interesting decisions carry a comment saying why, not what, which is most of the remaining bulk and is deliberate: you should not have to take my word for any of it.

Honest limits

  • Goods are checked, services are not. The server counts items into the client's hands. A service settles on the worker's word, deliberately: that is the part players should be arguing about, not the server.
  • No arbitration. No dispute queue, no staff tooling. Rejection is recorded against both parties and judged by neither.
  • Chromium is environment dependent. Both Skyrim Platform browser backends fail on my dev machine, so the console board is what I could photograph there. Mereth already pins NirnLab UI Platform, so the panel above is the path on your install.
  • Tested against a local server. Real skymp5-server, real ESPM data, one connected client. Not yet against Mereth's load or its modlist.
